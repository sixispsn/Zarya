# L05. Границы каталога водомеров

Дата: 21.09.2026. Согласовано пользователем отдельным продолжением после L04
и предложения перейти к L05. Исправление выполнено локально; production не обновлялся.

## Ошибка и контроль

Архивный `pickMeter` возвращает последний водомер, если ни один не удовлетворяет
условию Qсред ≤ Qэкспл. Python воспроизводил эту ошибку.

Контроль: Qсут=9600 м³/сут, T=24 ч, Qсред=400 м³/ч, qсек=120 л/с,
qчас=432 м³/ч. Архив выбирает DN250 с Qэкспл=380 м³/ч. При S=0,000018
потеря 0,2592 м проходит проверку, но не устраняет превышение Qэкспл.
Подтверждённый минимум также не может отменить эту независимую проверку.

Исправленный подбор:

| Qсут, м³/сут | T, ч | Qсред, м³/ч | Результат по среднему расходу |
|---:|---:|---:|---|
| 9120 | 24 | 380 | DN250 допускается; остальные проверки обязательны |
| 9600 | 24 | 400 | Подходящего водомера в каталоге нет |

## Основание и граница проверки

- Пункт 12.14 и таблица 12.1 СП 30: выбор по среднему часовому расходу за период
  водопотребления с ограничением эксплуатационным расходом, затем проверки 12.16.
  [Официальная публикация ФАУ ФЦС](https://api.faufcc.ru/api/assets/348e662a-c0ae-43ad-9ace-9c96309387b6),
  PDF-страницы 48–49 (печатные 43–44). Это базовое издание, не консолидированный
  текст всех изменений. Исправление также восстанавливает собственное условие
  `m.qexpl >= q_sr_hr` калькулятора; новые формулы не вводятся.
- При изменении таблицы ПЗ проверен п. 5.1.13 ГОСТ Р 21.619-2023: сведения
  об узле учёта и расчётные характеристики не должны изображать неподобранный
  прибор принятым. Полный состав ИОС2 и отдельный лист баланса не менялись.
- Существующие паспортные требования и согласованные исправления описаны в
  [предыдущем аудите водомеров](water_meter_audit_2026-09-20.md).

## Реализация

1. `pick_meter` возвращает `None` при исчерпании каталога. Неконечный или
   отрицательный средний расход не является допустимым входом.
2. Расчёт всех пяти ветвей (центральное ГВС: ХВС/ГВС; местное: ввод/ХВС/ГВС)
   выдаёт `MeterSelectionUnavailable`. API отвечает HTTP 400 с причиной,
   без фиктивного списка принятых приборов. T должен быть конечным и положительным.
3. При отказе общего пересчёта удаляются прежние результаты водомеров, их потери,
   пути напора и зависимый насос. Ошибка остаётся в проекте для интерфейса и ПЗ.
4. `app/pz/meter_validation.py` повторно вычисляет Qсред по текущим Qсут и T;
   Qэкспл берётся из канонического каталога по DN, не из сохранённого флага
   пригодности или подменённого значения Qэкспл. CALC-03 блокирует превышение;
   отсутствие данных не становится успешной проверкой.
5. Studio не показывает зелёный готовый подбор при ошибке или непроверенном
   среднем расходе. ПЗ показывает отказ либо «не подходит по Qсред» для старого
   сохранённого прибора. Потери неподобранного узла не подменяются нулём.

Каталог, повышение DN по потерям, пожарная проверка, обвод, паспортный минимум
и округление этим исправлением не заменены. Автоматического решения с параллельными
водомерами нет. Проверка среднего расхода не является полной актуализацией всех
характеристик старого проекта; паспорт и остальные проверки остаются отдельными.

Архив `legacy/sp30_calculator.html` не изменён, SHA-256:
`ace54b14e2f30fadaec768ec06aa5a326553709b9a869263208ef8ee58df3788`.
JS-oracle включает L05 отдельным флагом; исходное неверное поведение также
воспроизводится отдельным тестом. Числовой паритет внутри каталога сохранён.

## Проверки

- `tests/test_meter_catalog_bounds.py`: 31 тест — все границы каталога и соседние
  значения, пять ветвей, API, период, устаревшие результаты, зависимая цепочка,
  выпуск, ПЗ и явная поправка JS.
- Исполняемый JS/Python parity: 720 сценариев с явно включёнными DN65/L05.
- Широкий прогон: **2043 passed, 2 failed**. Оба падения — прежние ожидания
  `test_release_blocker_regression.py`, не учитывающие CALC-03 из-за отсутствия
  подтверждённых паспортных данных/минимального расхода DN40. Проверку не ослабляли,
  эти два теста данным исправлением не закрыты.
- Ruff и адресный mypy пройдены. Browser regression проверил обычный неполный
  подбор и отказ L05 без ложного зелёного статуса, мобильную ширину и отсутствие
  JS-ошибок. Для отказа использована изолированная подмена ответа в тестовой вкладке;
  реальный API отдельно проверен на границе 380 и превышении 400 м³/ч.
- `scripts/audit_legacy_port.py` подтверждает явный отказ L05, сохраняя результаты
  уже согласованных L01–L04.
