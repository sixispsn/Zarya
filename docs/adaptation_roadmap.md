# Roadmap адаптации Zarya

## Цель

Перевести Zarya из устойчивого закрытого пилота в воспроизводимый инженерный
продукт, пригодный сначала для комиссии и ограниченной экспертной эксплуатации,
а затем — для многопользовательской работы. Адаптация не заменяет расчётное
ядро и не меняет принятые инженерные алгоритмы незаметно для пользователя.

Целевой конвейер выпуска:

```text
ProjectIntent
    -> Fact Registry + Provenance
    -> Applicability / Preflight
    -> canonical calculation adapters
    -> Project
    -> document and drawing models
    -> normative + graphic audits
    -> immutable Release
    -> PDF / Proof / Defense / Digital Passport
```

## Неизменяемые гарантии

1. `legacy/sp30_calculator.html` остаётся каноническим источником рабочих
   алгоритмов В1, В2, Т3 и Т4 в границах `AGENTS.md`.
2. Перенос или рефакторинг расчёта принимается только при прохождении
   parity/golden-тестов. Эталон не обновляется молча.
3. СП, ГОСТ и ПП РФ № 87 задают применимость, проверки, состав выдачи и границу
   стадий П/Р, но не подменяют канонический алгоритм скрытой новой формулой.
4. Отсутствующие исходные данные не заменяются демонстрационными или
   «практическими» значениями.
5. ИОС2 проверяется по ГОСТ Р 21.619-2023, ИОС3 — по
   ГОСТ Р 21.620-2023 при каждой сборке.
6. Каждый этап должен завершаться рабочей версией, которую можно развернуть и
   при необходимости откатить. Большое одномоментное переписывание запрещено.

## Состояние, которое сохраняем

- расчёты расходов, напоров, водомеров, насосов и теплоизоляции;
- строгий нормативный слой В2 по СП 10.13130.2020;
- честные статусы `нет данных`, `стадия Р`, `ручная проверка`;
- самостоятельные комплекты ИОС2 и ИОС3;
- Proof, Defense, цифровые паспорта и контроль SHA-256;
- безопасный разбор проектов-аналогов без обучения расчётного ядра на них;
- файловый YAML как переносимый формат проекта.

## Этап 0. Зафиксировать базовую линию

**Результат:** воспроизводимая точка, относительно которой можно доказывать, что
адаптация ничего не сломала.

Работы:

- записать номер версии, commit, SHA-256 legacy-калькулятора и список редакций
  нормативов;
- закрепить полный успешный прогон тестов как baseline;
- сформировать набор контрольных проектов: жилой дом без В2, жилой дом с В2,
  общественное здание, смешанный объект, К1, К2 и К3;
- сохранить манифест выдачи каждого контрольного проекта: документы, страницы,
  ключевые расчётные показатели и SHA-256 PDF;
- составить реестр известных ограничений, не маскируя их под дефекты;
- заменить устаревший `STATUS.md` актуальным указателем на roadmap и текущий
  релиз либо удалить его как конкурирующий источник истины.

Критерии приёмки:

- полный набор тестов проходит;
- контрольные числа совпадают с текущей принятой выдачей;
- в Git хранится один однозначный baseline-манифест;
- существующий сайт продолжает работать без изменения поведения.

## Этап 1. Воспроизводимый и постоянный выпуск

**Результат:** проект и его выпущенный комплект не исчезают после перезапуска и
однозначно связаны с исходными данными, кодом и нормативной базой.

Работы:

- ввести `schema_version` в YAML с миграциями старых файлов;
- заменить прямую перезапись проекта атомарной записью через временный файл и
  `os.replace`;
- хранить ревизии исходных данных проекта, не только последнее состояние;
- создать постоянный `ReleaseStore` вместо `_RUNS` и `/tmp` как источника
  страницы результата;
- связать выпуск с `project_id`, ревизией YAML, commit сборки, legacy hash,
  нормативным baseline и полным манифестом документов;
- передавать `ZARYA_BUILD_COMMIT` при сборке Docker;
- восстанавливать Result, Proof и Defense из постоянного выпуска;
- определить политику удаления, архивирования и резервного копирования.

Критерии приёмки:

- результат и все ссылки открываются после перезапуска контейнера;
- изменение проекта создаёт новую ревизию и не меняет старый выпуск;
- старые YAML открываются через явную миграцию;
- повреждение входа или PDF обнаруживается проверкой целостности;
- два одновременных сохранения не создают частично записанный проект.

## Этап 2. Единая модель намерения проекта

**Результат:** ИОС2 и ИОС3 становятся равноправными разделами общего проекта,
а добавление вопроса не требует ручного дублирования логики во всех слоях.

Работы:

- ввести нейтральный `ProjectIntent` и общий `design_project()`;
- сохранить `IOS2Request` и `design_ios2()` как временные совместимые адаптеры;
- разделить данные на общие, ИОС2, ИОС3, архитектуру и технологию;
- создать `Fact Registry`: значение, единица, источник, статус подтверждения,
  применимость, нормативная ссылка и список зависимых решений;
- определить статусы факта: `confirmed`, `user_declared`, `derived`,
  `not_provided`, `stage_r`, `not_applicable`;
- перенести вопросы применимости в декларативные определения, используемые и
  сервером, и интерфейсом;
- сделать серверный Preflight единственным источником блокировок, предупреждений
  и списка уточняющих вопросов.

Критерии приёмки:

- старый YAML проходит round-trip без потери данных;
- расчётные результаты до и после адаптера идентичны;
- один новый вопрос описывается в одном правиле, а не отдельно в DTO, JS и HTML;
- каждый выводимый результат показывает происхождение использованных фактов;
- интерфейс не допускает выпуск при серверной блокировке.

## Этап 3. Один канонический генератор К1/К2/К3

**Результат:** сайт, полный комплект, архитектурный импорт и локальный экспорт
выдают одну и ту же принципиальную схему.

Целевая структура:

```text
Project.sewage
    -> WastewaterTopology
    -> WastewaterSP30Audit
    -> WastewaterDrawingModel
    -> LayoutEngine (standalone | confirmed AR)
    -> GraphicAudit
    -> SVG/PDF renderer
```

Работы:

- выбрать `WastewaterSchemeLayout` и новый renderer как единственную целевую
  графическую модель;
- добавить два адаптера компоновки: самостоятельная схема и схема по
  подтверждённой подложке АР;
- перенести в единую модель УГО, фасонные части, прочистки, ревизии, переходы,
  уклоны, марки труб, стояки, типовые этажи, выпуски и выноски;
- отделить нормативную необходимость элемента от выбора его конкретной
  конфигурации и координаты проектировщиком;
- запретить renderer создавать незарегистрированный инженерный элемент;
- переключить штатный `Комплект_К1_К2.pdf` на новый сервис;
- оставить старый генератор только как временный comparison backend;
- удалить старый production-путь после визуального и структурного parity.

Критерии приёмки:

- в production существует один публичный метод генерации схемы К1/К2/К3;
- один проект даёт одинаковый PDF из Wizard и архитектурного интерфейса;
- ни одна прочистка, ревизия или фасонная часть не зависит от случайной ветки
  renderer;
- структурный аудит не допускает висящих линий, неподключённых приборов,
  неверного направления стока и пересечений критических подписей;
- утверждённые контрольные схемы проходят визуальные golden-тесты;
- неполные исходные данные дают блокирующий статус, а не вымышленную трассу.

## Этап 4. Версионированная нормативная база

**Результат:** любой вывод можно связать не просто со строкой «СП 30», а с
конкретной редакцией и набором изменений, применённым при выпуске.

Работы:

- создать `NormativeBaseline` для каждого документа: обозначение, год,
  изменения, дата проверки, источник и SHA-256 локального эталона;
- присвоить каждому правилу стабильный ID, пункт, редакцию, входные факты,
  вердикт и уровень блокировки;
- отделить правила применимости от расчётных алгоритмов;
- формировать матрицы ГОСТ Р 21.619-2023 и ГОСТ Р 21.620-2023 машинно из
  результатов аудита;
- включить нормативный baseline в цифровой паспорт и комиссионный лист;
- добавить процедуру принятия новой редакции: анализ влияния, тесты, решение
  пользователя и новый baseline без изменения старых выпусков.

Критерии приёмки:

- каждый нормативный вердикт содержит точную редакцию и пункт;
- старый выпуск сохраняет прежний baseline после обновления норм;
- изменение нормативной таблицы невозможно без теста и записи об источнике;
- документы ИОС2/ИОС3 собираются только после профильного ГОСТ-аудита.

## Этап 5. Автоматические ворота качества

**Результат:** опасное изменение нельзя случайно развернуть на сайте.

Работы:

- настроить CI для Python 3.12;
- сделать обязательными legacy source-parity и расчётные golden-тесты;
- добавить постепенный lint и type-check сначала для новых/изменённых модулей;
- измерять покрытие критических модулей без требования искусственных 100%;
- добавить интеграционную сборку полного комплекта контрольных проектов;
- рендерить выбранные PDF в PNG и сравнивать утверждённые листы с допуском;
- добавить browser e2e: создать проект, пройти Preflight, сформировать комплект,
  скачать PDF, перезапустить приложение и снова открыть выпуск;
- собирать и проверять Docker image в CI;
- публиковать release notes с изменениями расчётов, нормативов и документов.

Критерии приёмки:

- merge невозможен при нарушении parity или нормативного аудита;
- Docker-сборка получает commit и проходит smoke-test;
- визуальная регрессия схем видна до публикации;
- релиз можно однозначно воспроизвести из Git и сохранённого ProjectIntent.

## Этап 6. Эксплуатационная надёжность и безопасность

**Результат:** Zarya готова не только к закрытому просмотру по одному паролю, но
и к контролируемой работе нескольких специалистов.

Работы:

- ограничить CORS реальными origin;
- добавить CSRF-защиту для изменяющих HTML-форм;
- ввести пользователей, организации, роли и владельцев проектов;
- разделить права просмотра, редактирования, выпуска и удаления;
- вести журнал действий и выпусков;
- добавить ограничения частоты и квоты для PDF/ZIP анализа;
- внедрить структурированные логи, correlation ID и безопасную страницу ошибки;
- автоматизировать резервные копии и проверку восстановления;
- определить сроки хранения проектов, импортов и цифровых паспортов;
- провести проверку зависимостей и базовый security scan.

Критерии приёмки:

- пользователь не видит чужие проекты и выпуски;
- удаление и выпуск отражаются в журнале;
- восстановление из резервной копии регулярно проверяется;
- внутренняя ошибка не раскрывает технические данные пользователю;
- открытие публичного доступа не зависит от общего Basic Auth.

## Этап 7. Минимальный интерфейс с уточняющим оркестратором

**Результат:** пользователь вводит минимум данных, но система не пропускает
необходимые инженерные уточнения.

Работы:

- заменить длинную единую форму последовательностью: объект → состав → ТУ/ТЗ →
  применимость → расчёт → контроль → выпуск;
- показывать только вопросы, активированные назначением, системами и уже
  введёнными фактами;
- красную лампу использовать только для блокирующих отсутствующих данных;
- отделить предупреждения, сведения стадии Р и рекомендации от блокировок;
- добавить автосохранение черновика и индикатор происхождения данных;
- перед расчётом показывать короткий Preflight: что готово, чего не хватает и
  какие документы будут сформированы;
- после расчёта группировать выдачу по `Общее`, `ИОС2`, `ИОС3`, не смешивая
  пояснения с обязательными действиями.

Критерии приёмки:

- обязательность поля определяется серверным правилом;
- пользователь может объяснить происхождение каждого автоматически заполненного
  значения;
- неизвестный ответ можно оставить неизвестным только с честным влиянием на
  готовность комплекта;
- учебный пример невозможно спутать с реальным проектом.

## Этап 8. База проектов-аналогов

**Результат:** прошедшие экспертизу проекты помогают контролировать полноту и
качество, но не меняют нормативные алгоритмы.

Работы:

- хранить права использования, тип объекта, регион, год, стадию, заключение и
  применённые редакции норм;
- сохранять извлечённые факты с документом и страницей;
- формировать типовые замечания и проверочные сценарии;
- использовать корпус как benchmark для ПЗ, спецификаций и схем;
- любые предложения по изменению правил проводить через отдельное инженерное
  решение, нормативный источник и тесты.

Критерии приёмки:

- проект-аналог не может автоматически изменить расчёт или нормативное правило;
- каждое извлечённое утверждение имеет ссылку на документ и страницу;
- персональные и договорные данные обрабатываются по заданной политике;
- корпус используется для оценки качества новых релизов.

## Этап 9. Расширение инженерного покрытия

Только после стабилизации этапов 1–5:

- расширение проверенных насосных каталогов с паспортными кривыми и версиями;
- каталоги регулирующей арматуры, водомеров и оборудования;
- улучшение распознавания АР и подтверждаемой привязки стояков/приборов;
- напорная внутренняя канализация как отдельный расчётный режим;
- дополнительные типы зданий и технологические анкеты;
- дальнейшее развитие спецификации и оценки объёмов стадии П.

Каждое расширение получает собственную границу применимости, источник данных,
тесты и статус точности. Оно не должно задерживать устранение архитектурных
рисков базового выпуска.

## Релизные вехи

| Веха | Состав | Назначение |
|---|---|---|
| `0.7 Stabilized Pilot` | этапы 0–1, build commit, постоянные выпуски | надёжный закрытый показ комиссии |
| `0.8 Unified Engineering` | этапы 2–4, единый генератор ИОС3 | единая воспроизводимая инженерная выдача |
| `0.9 Expert Beta` | этап 5 и интерфейс этапа 7 | ограниченная работа внешних проектировщиков |
| `1.0 Production` | этап 6, backup/restore, роли и аудит | многопользовательская эксплуатация |
| `1.x Knowledge` | этапы 8–9 | база аналогов и расширение инженерного покрытия |

## Первый исполнимый спринт

Спринт не затрагивает формулы и должен дать немедленное повышение надёжности:

1. Зафиксировать baseline тестов и шесть контрольных проектов.
2. Передавать commit в Docker и отображать его в цифровом паспорте.
3. Добавить `schema_version` с миграцией текущего YAML.
4. Сделать атомарное сохранение проектов.
5. Создать постоянный `ReleaseStore` и восстановление страницы результата.
6. Описать единственный целевой API генератора К1/К2/К3 и отметить старые
   entry points как deprecated, пока не переключая production.
7. Подключить минимальный CI: полный pytest, legacy parity и Docker smoke-test.

Спринт завершён только после проверки перезапуска контейнера, round-trip старого
проекта и выпуска контрольного комплекта без изменения расчётных показателей.

## Правило приоритета

Пока не завершены постоянные выпуски, единая модель проекта и канонический
генератор канализации, новые каталоги и эффектные функции не имеют приоритета.
Их ценность проявится только после того, как одна и та же подтверждённая модель
стабильно создаёт одну и ту же проверяемую выдачу во всех точках продукта.
