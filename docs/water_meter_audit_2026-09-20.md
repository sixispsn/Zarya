# Водомеры: legacy parity не равнозначна соответствию СП

Дата аудита: 20.09.2026. Обновление 21.09.2026: **три исправления согласованы
пользователем и выполнены в Python; оригинальный HTML сохранён**.
Разделы 1-3 ниже описывают состояние ДО исправления.
Каждая новая ошибка legacy требует отдельного обсуждения и разрешения (AGENTS.md, п. 16).

## Источники и границы проверки

- Выполняется исходный JavaScript из `legacy/sp30_calculator.html`: массив METERS,
  включая все его последующие перезаписи, `pickMeter`, `checkMeter`, `calcMeters`.
  Подменяется только представление результата, не арифметика или ветвления.
  Исполняемый блок SHA-256: `ebf419b2b1f38ec09277cc63b0f9048055ca55f3ef0625a52eb6e495a221ec3d`.
- [Официальная публикация СП 30 ФАУ ФЦС](https://api.faufcc.ru/api/assets/348e662a-c0ae-43ad-9ace-9c96309387b6):
  таблица 12.1, пп. 12.14-12.17, печатные страницы 43-45.
  Страница 44 с коэффициентами и формулой (18) проверена визуально, не только по OCR.
- Значение DN65 и требование проверки минимальных расходов также присутствуют
  в предоставленной сводной копии `СП 30.docx` (локальное извлечение
  `tmp/documents/norms-current/sp30.txt`, таблица 12.1, п. 12.16).
  [Карточка Росстандарта](https://protect.gost.ru/sp/details/8cd57a35-8503-4bb8-802a-324b64f3e0e7)
  перечисляет изменения 1-5. Полная нормативная сертификация ядра этим аудитом
  не выполнялась; старый PDF ФЦС не выдается за консолидированный текст изменений.

## 1. DN65: десятикратная ошибка коэффициента S

Таблица 12.1: `810 * 10^-5 = 0.0081 м/(л/с)^2`.
Исполняемый legacy: `METERS[6].S = 81 * 1e-5`, то есть `0.00081`.
Python `app/data/water_meters.py` перенёс последнее значение.

Контроль при q = 10 л/с, без изменения диаметра:

| Расчёт | S | h = S*q², м |
|---|---:|---:|
| legacy и текущая Zarya | 0,00081 | 0,081 |
| по таблице 12.1 | 0,0081 | 0,810 |

Это не дефект переноса: ошибка уже содержится в эталоне. Она может влиять
на выбранный DN, потери на вводе и требуемый напор насоса. Не означает,
что весь требуемый напор насоса занижен в десять раз.

## 2. Проверка минимального расхода не подтверждена

Legacy сравнивает `qthr <= q_hr`; Python делает то же. В конвейере
`flows_from_demand -> design_ios2 -> MeterInput` сюда поступает максимальный
расчётный часовой расход из водопотребления, а не минимальный.
П. 12.16в требует проверять возможность измерять минимальные расчётные
часовые расходы с учётом паспортного минимального расхода и класса счётчика.
Порог начала чувствительности из таблицы не заменяет этот паспортный параметр.

Таким образом, текущий положительный флаг `pass_sensitivity` не доказывает
выполнение п. 12.16в. Отсутствующий минимум нельзя заменить нулём,
максимумом или произвольной долей максимального расхода.

## 3. Дополнительно найдено различие округления Python/JS

На 720 сценариях (12 DN, три точки относительно порога выбора,
пять секундных расходов, с/без пожара, central/local):

- выбранные DN, проверки и примечания совпали;
- исходные значения таблицы численно совпадают, с учётом машинной точности;
- 30 результатов потерь расходятся на 0,001 м: DN200, q=10 л/с,
  Python показывает 0,003 м, JavaScript 0,004 м.

Причина: в JS S вычисляется как `3.5 * 1e-5`, Python хранит литерал
`0.000035`; получаются соседние двоичные значения около границы округления.
Кроме того, порядок умножений и правила округления Python/JS не тождественны.
Ни коэффициенты, ни округление в рамках аудита не исправлялись.

## Согласованные исправления от 21.09.2026

1. DN65: S = `810 * 1e-5`. Контроль q=10 л/с даёт 0,810 м.
   При q=20 л/с DN65 даёт 3,24 м > 2,5 м, поэтому выбирается DN80.
2. `pass_sensitivity` / `ok_v` теперь трёхзначные: true, false, null.
   Без отдельного минимального часового расхода, его основания и паспортного
   минимума выбранного DN проверка неизвестна. Максимальный часовой расход
   и порог чувствительности не используются вместо минимума. Нулевой явно
   заданный расчётный минимум не считается отсутствующим значением.
   После повышения DN паспорт старого диаметра не подтверждает новый счётчик.
3. Коэффициенты турбинных счётчиков вычисляются из тех же множителей,
   что в JS; порядок умножения h сохраняется. Округление выполняется
   с семантикой JS toFixed(3), а не Python round-even.

Три теста `test_legacy_meters_execution.py` теперь проходят. На 720 сценариях
сравниваются оригинальные JS-ветвления с единственной явной подстановкой
S для DN65 в памяти теста (`approved_dn65_correction=true`). Проверка
исходного HTML без подстановки сохранена: она подтверждает прежнее значение
и прежний SHA-256. Проверка минимума тестируется отдельно, поскольку это
согласованное отличие от legacy, а не parity.

`tests/test_meter_normative_corrections.py` проверяет числовые результаты,
неполные/невалидные входы, смену DN, API, YAML, конвейер, ПЗ и запрет
утверждать окончательный подбор без проверки минимума.
В Studio и ПЗ такие узлы отображаются как требующие данных/предварительные;
комиссионная проверка CALC-03 блокирует окончательный выпуск.
Расчёт потерь и предварительный просмотр остаются доступны.

Вход API `/meters/calculate`: `minimum_flow_checks` с ключами `total`, `cold`, `hot`.
В проектном YAML то же содержимое хранится в `source_data.meter_minimum_checks`:

```yaml
meter_minimum_checks:
  cold:
    dn_mm: 20
    q_min_hourly_m3h: 0.10
    q_min_passport_m3h: 0.05
    passport_reference: "Фактическая модель, класс, паспорт и страница"
    flow_reference: "Расчёт минимального расхода, лист"
```

Числа в примере только иллюстрируют формат, не являются настройками по умолчанию.
Значения задаются независимо для общего ввода, ХВС и ГВС; минимумы ХВС/ГВС
автоматически не суммируются. В полном редакторе эти исходные сохраняются;
при изменении потребителей/ГВС нужна повторная проверка. Специальный редактор
паспортов в Studio и автоматизация квартирных счётчиков в этот шаг не входят.

Визуально проверен расчётный PDF (3 страницы А4); состав блока учёта сверён
с ГОСТ Р 21.619-2023, п. 5.1.13. Отдельный баланс по п. 5.1.21 / форме 2
не изменялся. Это не заявление о полной нормативной проверке всего комплекта.

Поучастковая Т3 остаётся отдельным, ранее разрешённым расширением:
`docs/t3_hydraulics_2026-09-20.md`. Нельзя объявлять её legacy parity,
поскольку такого алгоритма в HTML нет.
