# ADR-001: единый API принципиальной схемы ИОС3

- Статус: принято как целевая архитектура, production пока не переключён.
- Дата: 2026-08-31.
- Область: К1, К2, К3; самостоятельная схема и подтверждённая подложка АР.

## Контекст

Сейчас штатный комплект вызывает `generate_wastewater_scheme_pdf()`,
архитектурный интерфейс — `generate_wastewater_structure_pdf()`, а сборочные
контрольные листы используют отдельный building drafter. Исправление УГО или
монтажного узла поэтому может попасть только в один путь выдачи.

## Решение

Единственной будущей публичной точкой входа становится сервис со следующим
контрактом:

```python
result = wastewater_scheme_service.build(
    project=project,
    mode="standalone" | "confirmed_architecture",
    confirmed_layout=layout_or_none,
    diagnostics=False,
)

result.drawing_model
result.normative_audit
result.graphic_audit
result.svg
result.warnings

wastewater_scheme_service.write_pdf(result, output_path)
```

Сервис обязан выполнять стадии строго в одном порядке:

```text
Project.sewage
  -> WastewaterTopology
  -> WastewaterSP30Audit
  -> WastewaterDrawingModel
  -> LayoutEngine
  -> GraphicAudit
  -> SVG/PDF
```

## Инварианты

1. Renderer не создаёт трубопровод, прибор, прочистку, ревизию или фасонную
   часть, отсутствующую в подтверждённой модели проекта.
2. Нормативный аудит определяет необходимость и доступность обслуживания, но
   не выдумывает конкретную конфигурацию фасонной части и её координату.
3. `standalone` и `confirmed_architecture` различаются только источником
   компоновки. Топология, УГО, подписи, аудит и PDF renderer у них общие.
4. Диагностический слой движения стока не становится частью нормативного УГО.
5. При блокирующем аудите сервис возвращает результат проверки, но не маркирует
   схему как готовую к выпуску.
6. Один `ProjectIntent` при одинаковом commit и нормативном baseline даёт один
   и тот же drawing model независимо от HTTP-маршрута.

## Миграция

1. Зафиксировать контрольные PDF всех действующих backend.
2. Ввести фасад сервиса без переключения production.
3. Перенести новый structure renderer за фасад.
4. Добавить standalone layout adapter.
5. Перенести УГО и монтажные узлы из старого renderer в drawing model.
6. Сравнить структурные аудиты и утверждённые визуальные golden-листы.
7. Переключить Wizard, комплект и архитектурный интерфейс на фасад.
8. Оставить старые функции как deprecated на один релиз.
9. Удалить старый production-путь после подтверждения контрольных проектов.

До шага 7 текущий комплект продолжает использовать прежний генератор. Этот ADR
не разрешает частично переключать отдельные HTTP-маршруты без общего сервиса.
