# Привязка потерь пути всасывания

15.10.2026, продолжение L08. Новых гидравлических формул, коэффициентов и
автоматически назначенных исходных нет. Это слой проверки полноты и суммирования
готовых результатов, а не исправление legacy или решатель кольцевой сети.

## Что реализовано

`app/pz/water_station_suction.py` получает действующий граф ВУ/насосной и
закрытую арматуру из `review_station`. Возвращает альтернативные пути от
границ вводов до всасывающего патрубка каждого насоса. Обратные клапаны
учитываются по направлению; чужой насос и внешняя сеть не служат транзитом.
Обводы Г.1 остаются закрытыми. Корпус насоса и его напорная арматура за границей
Hf. Поиск ограничен; обрыв поиска никогда не подтверждает полноту.

Каждый путь содержит `required_components`: тела на пути (`node:…`) и
соединения (`link:…->…`). Эти ID взяты из текущего графа, не из координат
рисунка. Соединение не означает дополнительную деталь спецификации или
назначенную длину. Потери группы труб/фасонины можно привязать одной записью
с покрытием нескольких ID.

`app/calc/suction_losses.py` проверяет такие записи:

- каждый компонент имеет только одного владельца потерь;
- неизвестные/посторонние ID и повторный учёт отклоняются;
- расход соответствует явно заданному максимальному режиму, температура совпадает;
- у значения есть основание; явный обоснованный ноль допустим, пустота не равна нулю;
- готовые потери уже с местными не получают вторую процентную надбавку;
- при неполном покрытии `total_loss_m=null`, отдельно видны известная часть и пробелы;
- никаких пересчётов пропорционально Q² или подстановок Qрасч вместо Qmax нет.

Покрытие — ответственность явно заданного расчётного состава. Оно не
подтверждает достоверность произвольного введённого числа/каталожного основания.
Схемный граф сам по себе не даёт размеров труб и паспортных сопротивлений.

## API и границы интеграции

Существующий `POST /pumps/npsha` принимает необязательный `suction_path`:

```json
{
  "required_components": ["pipe", "meter", "filter"],
  "path_basis": "Границы, режим арматуры и основание расчёта",
  "losses": [
    {
      "id": "pipe-result",
      "covers": ["pipe"],
      "loss_m": null,
      "flow_m3h": null,
      "temperature_c": null,
      "basis": ""
    }
  ]
}
```

Это вложенный объект, не полный запрос. Режим Qmax/T берётся из внешних полей
NPSHa. Одновременные готовый `suction_losses_m` и состав пути запрещены.
Полная привязка передаёт Hf в существующий баланс CNP; неполная оставляет
его незавершённым. Ответ сохраняет исходные, трассировку и effective Hf.
Старый запрос только с готовым Hf совместим. Суммы не округляются до проверки.

Первый этап вернул `water_station_review.suction_paths` из текущего проекта.
На тот момент формы редактирования/сохранения в Studio ещё не было;
её продолжение описано ниже. Перенос в YAML пока не реализован.
Публичный API принимает явный состав, не сверяет его с сохранённым проектом и не
обновляет проект/подбор. Поэтому старый внешний JSON нельзя представлять как
повторно проверенную актуальную привязку после изменения проекта.

## Самара

В контрольном общем ВУ Г.1 найдено 8 альтернативных маршрутов: 2 ввода ×
2 выходные магистрали × 2 насоса. Это НЕ восемь одновременно суммируемых
потерь и НЕ восемь насосных режимов. Распределение по параллельным ветвям
не рассчитано, Q/2 не назначается. Связность не подтверждает пропускную
способность или единственность пути. Для применения последовательной суммы
нужно явное основание соответствующего режима; произвольный кратчайший путь
не выбирается.

Старые потери водомера/труб при Qрасч не перенесены как Hf при Qmax. NPSHa
Самары по-прежнему не подтверждён: нет полного максимального режима, оси
насоса и потерь всех частей соответствующего пути. Snapshot, ПЗ, PDF, СО,
расходы и подбор не менялись. Новые вопросы пользователю не навязываются.

## Проверка

`tests/test_suction_losses.py` проверяет готовые результаты канонического
`calculate_v1_hydraulics`, отсутствие второй надбавки, недостающий фильтр,
повторное покрытие, ошибочный режим, нулевые значения, переполнение, пути Г.1,
один ввод, отсечение ввода, отсутствие обхода закрытого счётчика, ограниченный
поиск и полный сценарий API → состав потерь → существующий NPSHa. Условные
числа тестов не записываются в Самару.

## Продолжение: необязательная проверка в Studio

Добавлен свёрнутый блок «Проверка всасывания» после обычного расчёта проекта
с поддержанной насосной В1. В окне выбирается один маршрут; пользователь
задаёт основание последовательного режима, максимальную подачу и температуру.
Давление, отметки, Hv и NPSHr находятся в отдельной раскрываемой группе.
Одна строка готового результата может покрывать несколько элементов/соединений.
Нет значений по умолчанию для потерь, подачи, отметок, Hv или давления;
Hs=0,5 м явно показан как минимум принятой методики CNP.

Проверены существующие данные:

- `metering_products.json` и `MeterPressureLossLimit` содержат только паспортный
  верхний предел ДЕКАСТ при Qmax. Его нельзя превращать в точную h(Q).
- `metering_products_flanged.json` содержит геометрию IS16, но не характеристику
  сопротивления фильтра. В `metering_products_20261012.json` отмечен конфликт
  Kv арматуры; в расчёт эти значения не перенесены.
- Готовые результаты участков В1 включают местные потери. Их прежний режим
  не объявляется максимальным режимом всасывания; дополнительного умножения нет.

`GET /studio/api/suction` и `POST /studio/api/suction` заново строят проект
штатным конвейером без документов. `studio_suction.py` проверяет маршрут по
текущему графу и связывает ввод с отпечатком всех исходных/результатов проекта,
графа и закрытой арматуры, расчётного кода и каталогов. Изменение длины,
отметки, потерь, выбранного изделия или каталога отзывает прежнюю актуальность,
даже если состав ID не изменился. Явная ось насосной проверяется на совпадение
с введённой осью баланса; неизвестная отметка не заполняется.

Проверка сохраняется в `draft.suction_check` с исходными. При открытии
результат вычисляется снова; устаревший результат не возвращается. Повторное
принятие прежних значений после изменения контекста требует явной отметки
проектировщика о перепроверке. Она не доказывает точность введённых потерь:
числа и основания внешнего расчёта остаются ответственностью задающего их.
Повторное покрытие, чужой маршрут и произвольный подменный состав отклоняются.
Версия черновика и штатная изоляция доступа действуют и для этой операции.

Граница этапа: сохранение только в рабочем черновике Studio. В Project/YAML,
подбор, ПЗ, PDF, СО и архив версий пилота проверка пока не переносится.
Подписанные учебные примеры не редактируются через новый экран. Для Самары
проверен явно подготовленный общий Г.1 через тот же сервис: 8 альтернативных
путей, неизменность исходного Project; числа арифметических тестов не назначены
Самаре. Её NPSHa остаётся неподтверждённым.

Контроль: `tests/test_studio_suction.py` и профильный набор NPSHa/путей/насосной;
профильный прогон — 130 passed; после добавления отдельной проверки длины
повторно прошли все 12 тестов нового модуля. Ruff новых Python-файлов,
синтаксис JS, воспроизводимость рабочего HTML и архивный SHA проверены.
`scripts/verify_studio_suction.cjs` — сохранение, перезагрузка, неверный режим,
устаревший контекст, явная перепроверка и экран 390 px. Скриншоты:
`output/ui/studio-suction/`. В расширенном прогоне выявлен отдельный старый
тест `test_meter_products.py::test_local_heater_three_nodes_counts_and_control_values`:
он ожидает 2 вводных счётчика, хотя текущий `make_draft` получает общий ВУ и
выдаёт 1. Код подбора/спецификации и этот эталон данным этапом не менялись;
расхождение не скрыто заменой ожидаемого значения.

## Продолжение 15.10.2026: Project, YAML и выдача

Граница предыдущего этапа снята для сохранения и представления, но не для
автоматического подтверждения подбора/станции. `ProjectSuctionInput` хранит
только явные исходные, ID пути и отпечаток привязки. Поле `suction_check`
необязательно в IOS2Request, Project и YAML; старые проекты без него не
получают новый расчёт. Служебные revision/reviewed остаются только в Studio.
Кэшированный результат в структуре YAML отклоняется схемой. Полный редактор
сохраняет эти исходные, но не обновляет их отпечаток за пользователя.

Общий сервис `app/pz/suction_check.py` используется Studio и генератором
документов. Текущие результаты пересчитываются, а при другом проекте/каталоге
возвращается stale без чисел. Неподдержанная схема или недопустимые исходные
дают invalid без результата. Сама проверка исключена из своего отпечатка,
как и шифр, штампы и цифровой паспорт. Эквивалентные числа 0 и 0.0 не
создают ложное устаревание после YAML; дробные числа не округляются.
Изменение размеров/потерь/изделия сохраняет обязательный отзыв результата.
Старая версия привязки требует явного reviewed, без автоматического признания.

В отдельном расчёте насосов и в ПЗ жилых/общественных объектов добавлен один
общий шаблон `suction_check_table.html`: явный путь/режим, исходные,
покрытие готовых потерь, методика и отдельный вывод. Для абсолютного давления
атмосферное не требуется и не запрашивается таблицей. Для неполного пути
Hf/NPSHa не подтверждаются. Устаревший вывод остаётся предупреждением без
старой таблицы результата, в том числе если насос больше не требуется.
Внешние потери и NPSHr не становятся паспортными данными от факта вычисления.
Свойства `project.pumps`, алгоритм выбора, СО и общий статус станции не меняются.

Сохранение Studio обновляет сводку и отпечаток расчёта, отзывает текущие
ссылки preview/package и создаёт новую передачу проекта при изменении
проверки. Физические PDF старых версий не удаляются. В существующем opt-in
пилоте исходные/результат включены в неизменяемый снимок; новый адрес доступен
только после персонального входа и согласия, в пределах своего черновика.
Общий handoff в старый редактор по-прежнему не открыт участникам пилота.

Контроль: `tests/test_project_suction.py` (YAML roundtrip, самопривязка,
устаревание по геометрии/каталогу/модели, полный редактор, отчётность и версии
пилота), прежние профильные/parity тесты и браузерный сценарий.
`scripts/verify_project_suction.py` воспроизводит синтетический PDF на 4 листах,
ПЗ на 10 листах, отдельный А3-баланс формы 2, неполный и устаревший случаи.
Использован штатный генератор; проверены рамки/штампы, полные таблицы и
неразрывность вывода с перечнем недостающих данных. Состав ПЗ и баланса
проверен по существующей матрице ГОСТ Р 21.619-2023 и тестам формы 2;
эта синтетическая проверка не объявлена полным реальным комплектом ИОС2.

Финальный расширенный прогон: 305 passed / 4 failed. Включены персональный
доступ и создание новой версии пилота после сохранения проверки; чужой
черновик отклоняется защитой выбранного проекта (409), анонимный запрос -
401, межсайтовая запись - 403. Четыре сбоя
`tests/test_project_store.py::test_form_prefill_renders_saved_values`,
`test_form_prefill_preserves_selects`, `test_form_without_prefill_has_no_demo_document_data`,
`test_projects_page_template` вызваны рендером без request в `site_assets.html`;
данные шаблоны и тесты не менялись. Это отдельный открытый технический долг.
Legacy и архив воспроизводимы; подписанный пример и 81-страничный PDF Самары
не перезаписаны. Production не обновлялся.
