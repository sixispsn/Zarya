# Белая ЗАРЯ: основное рабочее место

Главная страница теперь ведёт на `/studio`; интерфейс включён по умолчанию.
Для отката маршрута достаточно `ZARYA_STUDIO_ENABLED=0`: главная снова откроет
`/wizard`, API studio будут недоступны, сохранённые данные не удаляются.
Белое рабочее место выложено на сервер 22.09.2026; состав снимка, проверки и
откат описаны в `docs/deployment_2026-09-22.md`. Сам редизайн не меняет формулы:
в релиз включены отдельно согласованные исправления legacy (AGENTS.md, 14–23).
Ранее исправлена передача
готового К1 между модулями: повторное сложение после округления давало ошибку
0,001 л/с и останавливало конвейер для 20 жителей. Исполняемый legacy подтвердил
2,293 л/с; тест проверяет и ядро, и итоговый Project.

## Что работает

Уточнения (22.09.2026): после загрузки документов или расчёта открывается одна
прямоугольная карточка с недостающими исходными. Вопросы берутся из прежнего API,
новые обязательные расчётные поля не добавлены. Подробные трассы В1/Т3 остаются
в ручном редакторе. Карточку можно закрыть кнопкой «Позже», крестиком или Escape;
неприменённый ввод остаётся в текущей форме и восстанавливается при открытии.
После перезагрузки сохраняются только подтверждённые сервером изменения.

Для найденных в PDF значений показано не более трёх подтверждений за раз:
скрытые кандидаты не принимаются нажатием «Продолжить» в другой карточке.
Красный индикатор — насыщенный `#FF123B`, плавный цикл 2,4 с без полного гашения;
готовые результаты имеют постоянное зелёное свечение. При reduced motion
индикация и появление статичны. Native dialog обеспечивает клавиатурный фокус.
Проверки: `tests/test_studio_questions.py`, `tests/studio_questions.test.cjs`.

1. Белая стартовая страница и подъём существующего логотипа из-за линии горизонта.
   Загрузкой можно пользоваться во время анимации; reduced motion поддерживается.
2. Загрузка нескольких PDF с сервера приложения, без внешних ИИ-сервисов.
3. Из текстового слоя извлекаются только явно подписанные скалярные значения:
   жители, этажность, квартиры, общая и пожарно-техническая высоты, гарантированный
   напор, максимальный сброс прибора. Нет пересчёта давления в этажность или
   определения жителей по квартирам.
4. Каждый кандидат имеет имя PDF, страницу и точную цитату. До подтверждения
   кандидат не считается расчётным исходным. Несогласованные источники требуют
   явного выбора. Новый противоречащий PDF повторно открывает вопрос.
5. Для жилого дома с одной группой потребителей первый экран — единая форма:
   жители, этажи, квартиры и непосредственно доступные списки приборов/ГВС/кровли.
   По явному пожеланию пользователя показаны стартовые варианты: ванна ≥1500 мм,
   централизованное ГВС, плоская неэксплуатируемая кровля. Это не новые defaults расчётного ядра:
   до отправки видимой формы они не входят в принятые исходные. Одно нажатие
   «Рассчитать» принимает показанные значения с происхождением `residential_preset`.
   Ранее введённое и найденное в PDF не заменяется пресетом. Жители, отметки,
   потери, площади и напор не заполняются предположениями. q₀s = 1,6 л/с
   берётся из принятого значения DTO/ядра без отдельной карточки или вопроса.
   Изменить его можно в «Ручном вводе». Найденный в PDF другой q₀s нельзя молча игнорировать:
   он требует подтверждения. Hпр = 20 м и количество вводов = 1 также имеют
   видимое происхождение из существующих настроек ядра.
   Дополнительные параметры раскрываются одним действием в «Ручном вводе», без
   промежуточных кнопок «Уточнить». Неполные данные не блокируют именно расход.
6. Реальные расходы вызывают существующую `calculate_water_demand` без новых
   формул/коэффициентов. Отдельно показаны общий, холодный и горячий потоки и К1.
7. Подтверждённые данные сохраняются между перезагрузками. Черновик доступен через
   случайный идентификатор в HttpOnly/SameSite=Strict cookie, PDF — только в рамках
   этого черновика. Идентификатор не передаётся в ссылках на страницы проекта.
8. Кнопка «Рассчитать» принимает форму одной транзакцией и вызывает обычный
   `IOS2Request → build_project → design_ios2(render_documents=False)`, если
   заданы этажность, обе высоты, ГВС и найденные исходные. В том же белом интерфейсе
   показываются водомеры, В2, напор В1/Т3, насосы, К2 и границы циркуляции Т4.
   Недостающие отметки/потери не подставляются. Параметры напора и дождя доступны
   в ручном вводе. Несохранённое редактирование скрывает устаревший результат;
   форма сохраняется при расчёте, по отдельной кнопке либо при обычном переходе
   в другой раздел. Выход с несохранёнными изменениями вызывает предупреждение.
   Ошибка или устаревшая ревизия не сохраняет форму частично.
9. «Посмотреть схему» и «Открыть ПЗ» собирают существующие документы в приватной папке черновика,
   без публикации паспорта/выпуска. Это явно помеченный в интерфейсе предпросмотр,
   не готовый проект. Ссылка проверяет cookie, ID текущего предпросмотра и список
   его файлов. После изменения исходных старые ссылки отзываются.
10. «Скачать комплект» — отдельное действие через общий
    `wizard.design_request_response`, с обязательными quality gates. Матрицы
    ГОСТ ИОС2/ИОС3 проверяются уже при расчёте, а не только после рендера.
    Отсутствие обязательных сведений нельзя выдать за готовность всего комплекта.
    После успешного выпуска все фактические PDF скачиваются одним ZIP-архивом.
    Архив доступен только текущему черновику; после изменения данных прежняя
    ссылка отзывается. Из предпросмотра скачать архив готового комплекта нельзя.
11. Расширенный редактор оставлен дополнительным путём для сложной топологии,
    дополнительных групп и остальных входов. Повторный переход с теми же исходными
    не перезаписывает уже изменённый проект. Источники сохраняются в studio;
    поэлементный перенос происхождения в паспорт остаётся следующим этапом.
12. Главная, редактор, проекты, модель здания, планы, анализ и нормативная база
    используют общую белую оболочку. В шапке только «Проект», «Мои проекты» и
    раскрываемое меню инструментов, без прежней длинной панели. Старое предпочтение
    тёмной темы не перекрашивает эти страницы; режим защиты проекта не изменён.
13. «Мои проекты» показывает текущий studio-черновик данного браузера отдельно от
    карточек сохранённых YAML-проектов. Старые проекты открываются без миграции и
    потери исходных в полном редакторе. Создание отдельного проекта остаётся в нём.
    Переход из studio в расширенный редактор через меню переносит подтверждённые
    данные существующим handoff, а не открывает пустую форму.

## Короткий путь после первого расчёта (20.09.2026)

### Выбор кровли

- В списке пять вариантов: односкатная, двускатная, сложная/составная,
  плоская эксплуатируемая и плоская неэксплуатируемая. Studio и полный редактор
  показывают компактный силуэт выбранной крыши. Это UI-подсказка, не модель АР:
  координаты силуэта не передаются в расчёт или PDF.
- Выбор передаётся в существующие контракты дождя (`flat`/`sloped`) и вентиляции
  канализации. Подсказка берёт минимальную высоту из общей таблицы валидатора
  и чертёжного модуля: 0,2 м для скатов/неэксплуатируемой кровли, 3 м для
  эксплуатируемой с проверкой группы минимум из четырёх стояков. Трассы не выдумываются.
- Старые неопределённые `flat` и `sloped` сохраняются, но не показываются как
  дополнительные варианты списка и не заменяются конкретной формой автоматически.
  Для них виден плейсхолдер и пояснение под полем; сохранение других параметров
  не стирает старый вид кровли. У скатов нужна отметка кровли в месте фанового
  выхода, не только отметка конька.
- `complex` сохраняется в DTO/YAML как самостоятельный вид. Он может включать
  скаты и эксплуатируемые террасы, поэтому глобальный fan minimum отсутствует,
  дождевой тип остаётся `not_set`, готовность схемы явно заблокирована.
  Следующее развитие — участки кровли с геометрией, отметками, доступностью,
  водосборами и привязкой каждого фанового выхода, а не одна высота на здание.
- Две учебные компоновки имеют фиксированную геометрию. Несовместимый выбор
  сохраняется, но прежние PDF отзываются и экспорт блокируется с видимым
  объяснением. Изменение списка не означает поддержку новой геометрии учебного разреза.
- Проверка: 169 тестов Studio, вентиляции, стояков и передачи геометрии;
  `scripts/verify_studio_roofs.cjs` проверяет пять вариантов, сохранение, подсказки,
  силуэты в обоих редакторах, сохранность старых значений при посторонних правках,
  незаданную высоту составной крыши и блокировку несовместимого учебного PDF.
  Внешний вид проверен на 1280 и 320 px. Изменения пока только локальные.

### Контекстные шаги

- Исходная форма сворачивается в строку «Исходные данные», остаётся редактируемой.
  Расходы кратко видны сразу; все таблицы и технические проверки — в раскрытии.
- Открыта одна карточка недостающих данных: документальные кандидаты, здание,
  ввод/перепад отметок или дождь. Уже принятые значения не спрашиваются.
  Списки доступны сразу, без промежуточного «Уточнить».
- Можно перейти к другой группе, например посчитать дождь, пока нет трассы
  для потерь. Неизвестный напор от этого не становится рассчитанным. Вопросы
  ГВС не появляются при выбранном отсутствии ГВС; теплообменник спрашивается
  только при его включении в расчётный путь.
- Карточки используют тот же атомарный API формы: один источник значений,
  проверка ревизии, серверная валидация, отзыв устаревших PDF. Неуспешная
  отправка не стирает локальный ввод. Ручной ввод всех полей остаётся доступен.
- У документов три основных действия: схема, ПЗ, комплект. В списке схем
  неполная топология явно отмечена как каркас. Кнопка «Что осталось» раскрывает
  реальные проверки; отсутствие вопросов в простой форме не равно готовности
  ИОС2/ИОС3. Топология и полный состав исходных по-прежнему в редакторе.

Проверка 20.09: 154 backend/regression-теста и 63 теста схемы/legacy; оба браузерных сценария (PDF и
ручной старт, включая ширину 320 px) проходят. На 20 жителей: 3,6 м³/сут,
К1 2,293 л/с; Москва / 252 м² / стены 0: К2 5,395 л/с. Потери 3 / 1 / 0,5 м
и hгеом 6 м используются только в изолированном QA-сценарии, не как исходные
реального двухэтажного проекта. Подтверждение всех рабочих потерь ещё нужно.
Согласованный отдельный учебный разрез 8 квартир пересобран существующим
CLI с исполняемой проверкой legacy; он не подставляется вместо отсутствующей
топологии любого проекта в studio. Шаблоны ПЗ и схема не менялись этим UI-шагом.

## Учебные схемы в Studio (20.09.2026)

«Попробовать на примере» открывает отдельный приватный черновик. Доступны
согласованные компоновки 2 этажа / 8 квартир и 3 этажа / 12 квартир. Возврат
восстанавливает прежний проект; загрузка реальных PDF и handoff в этом режиме
запрещены, выпуск комплекта всегда заблокирован.

Меняются жители, город и площадь кровли. Геометрия, благоустройство, водосборы,
уклоны и материалы явно относятся к выбранному учебному варианту. Это два
ограниченных генератора, не распознавание произвольного плана и не универсальное
редактирование этажности. Выбор другого варианта открывает его исходные значения.

Снимок шаблона хранится в черновике. Расходы экрана, схемы, ПЗ ИОС3 и баланса
получаются из одних исходных; публикация PDF требует совпадения с исполняемым
legacy. Любая правка отзывает старый предпросмотр. У документов общий хеш модели.
ПЗ ИОС3 использует прежние шаблоны и нормативный аудит: незаданные ТУ, трассы,
абсолютные отметки и фактическое обслуживание остаются незаданными. Учебные
профили не подменяют подтверждённую проектную ведомость труб. Напор и В2 не
вычисляются ради получения учебного PDF канализации.

Двухэтажное приложение больше не привязано к 20 жителям / 252 м²: эти значения
сохранены как эталон, но текущие жители и площадь доходят до расчётных листов.
В Docker добавлены Node.js, исходный HTML и узкий скрипт проверки legacy.
Локально нужен `node` в PATH либо `NODE_BINARY`; без него экспорт закрыт.
Проверка: `tests/test_studio_study.py` и `node scripts/verify_studio_study.cjs`.

При визуальной проверке убрано вводящее в заблуждение равенство из округлённых
слагаемых К1 в ПЗ/расчётном листе: формула сохранена, слагаемые показаны справочно,
итог берётся из legacy до округления. Ядро и эталонные числа не изменены.
Проверены обе PDF-схемы и все страницы обеих ПЗ; изменение на 50 жителей / 200 м²
проверяется также по тексту реально сгенерированных PDF. Три браузерных сценария
проходят, включая отзыв PDF, возврат исходного черновика и мобильный экран.

## Границы

### Расчётный путь В1 в Studio (20.09.2026)

В ручных настройках нового черновика потери труб можно вводить участками:
длина, точный внутренний диаметр, шероховатость, расход и назначение участка.
Используется существующий `calculate_v1_hydraulics`, новых гидравлических
формул в Studio нет. Коэффициент местных потерь определяется типом сети.
Названия материалов не подменяют известную шероховатость или внутренний диаметр.

На вводе незаданный расход пересчитывается по текущим потребителям: ХВС при
внешнем ГВС, суммарный при местном приготовлении/своём ИТП. Во внутренней
ветви расход задаётся явно, общий расход дома не распространяется на все ветви.
Нужны и ввод, и внутренняя часть; отсутствие одной части не даёт нулевые потери.
Старые черновики сохраняют режим готовых сумм. В режиме участков готовые суммы
В1/ввода игнорируются, а при редактировании старые результаты и PDF отзываются.

Один путь В1 не является рассчитанной трассой Т3. Новый признак
`internal_losses_scope=cold_only` запрещает перенос потерь В1 в Т3. Для Т3
есть отдельный редактор участков и альтернативный ввод готовой суммы
(`h_il_hot_m`), без водомеров/нагревателя. Методика — явно согласованное
расширение по СП 30, см. `t3_hydraulics_2026-09-20.md`.
Без необходимых данных о циркуляции и пределе скорости итоговый общий подбор
не объявляется завершённым. Превышение скорости блокирует выпуск.
С 21.09 предварительный квартирный водомер может рассчитываться по явно
согласованной средней заселённости; это не определяет расходы участков трассы
и не подтверждает диктующую квартиру (см. правило 23 в AGENTS.md).

Участки и область применения потерь сохраняются в YAML и при переходе в полный
редактор. Там путь пока только сохраняется; при изменении потребителей или
источника ГВС форма просит пересчитать его в исходном Studio-проекте. Передача
в полный редактор фиксирует текущие расходы участков как расчётный снимок.

### Продолжение работы без трассы на стадии П (22.09.2026)

Карточка «Напор: расчётный путь» исключена из обязательного опроса. После
исходных по вводу пользователь переходит к дождю. Поучастковый редактор и ввод
готовых сумм остаются в ручных настройках; доступ к ним необязателен для
продолжения работы. Методика потерь и рабочий legacy не менялись.

После основных данных здания и успешной валидации исходных доступен приватный
черновик PDF, даже если напор не рассчитан. В ПЗ, расчётном листе В1/Т3 и листе
насосов явно указаны неполнота расчёта и отсутствие подтверждённого подбора.
Неизвестные потери остаются неизвестными, не нулевыми. Полный холодный путь
при незавершённом горячем не подтверждает общую насосную установку.

Это не отменяет обоснование напора и состава ИОС2/ИОС3: выпуск комплекта
по-прежнему проходит preflight, нормативные матрицы и quality gates. Признаки
приватного просмотра не записываются в исходный YAML и не меняют штамп проекта.
Проверки: `tests/test_studio_stage_p_preview.py` (включая реальную сборку PDF),
`tests/test_studio_hydraulics.py`; браузерный сценарий без трассы.

### Общие ограничения

- Основной упрощённый сценарий — жильё, одна группа потребителей. Полная форма
  сохранена как расширенный редактор; смешанные функции пока доступны в нём.
- Сканы и планы сохраняются и открываются, но OCR и определение планировки
  отсутствуют. Слово «прочитан» относится только к текстовому слою PDF.
- Норма потребления выбирается пользователем из существующего каталога.
  Неоднозначные числа, диапазоны, единицы давления и неподдержанные формулировки
  не превращаются автоматически в исходные параметры.
- Полная геометрия сетей и редактирование всех технических/текстовых исходных
  пока не перенесены в виджеты. Предпросмотр не создаёт недостающую топологию,
  планы, метраж труб или конечную гидравлику из числа квартир.
- Нет управления историей studio-черновиков и удаления через интерфейс: в браузере
  один текущий черновик. В Compose его PDF и данные хранятся в постоянном томе
  `/data/projects/_studio`; резервное копирование тома должно включать эту папку.
- Существующая парольная защита Caddy сохранена. Сам FastAPI не имеет отдельной
  авторизации: нельзя публиковать его порт в обход Caddy. До многопользовательского
  запуска остаются учётные записи, пользовательские квоты и изоляция PDF-парсинга.

## Локальный запуск

```sh
venv/bin/python -m pip install -r requirements.txt
ZARYA_STUDIO_ENABLED=1 \
ZARYA_STUDIO_DIR="$PWD/output/studio-preview/drafts" \
ZARYA_PROJECTS_DIR="$PWD/output/studio-preview/projects" \
ZARYA_NORMATIVE_MONITOR_ENABLED=0 \
venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8766
```

Открыть `http://127.0.0.1:8766/`. Используется отдельная папка проектов,
не пользовательские рабочие выпуски.

## Проверки

### Квартирные водомеры (21.09.2026)

В обычном опросе больше нет ручного задания потерь квартирных счётчиков.
Для централизованной ГВС и сценария без ГВС разрешена предварительная оценка:
число жителей / число квартир → существующий расчёт расходов → существующий
подбор водомеров и h=S·q². Дробная средняя заселённость не округляется.
На примере 20 жителей / 8 квартир получены DN15: ХВС 0,633 м, ГВС 0,708 м.
Это допущение, а не установленная диктующая квартира; оно сохраняется в YAML,
передаётся в пояснение ПЗ и требует подтверждения перед окончательным выпуском.
Ручные потери/заселённость доступны в «Ручном вводе» и имеют приоритет.
Для местных водонагревателей неизвестная схема квартирного учёта не угадывается.

Потери ИТП/водонагревателя находятся только в ручных настройках и видны при
включении его в расчётный путь. Автоматические 3 м пока не введены: это отдельное
согласование. Отсутствующее сопротивление не заменяется нулём.
Готовые расходы теперь отделены от незавершённого напора. Красные индикаторы
плавно пульсируют (1,8 с), зелёные светятся постоянно; reduced-motion отключает
пульсацию, сохраняя цвет и поясняющий текст.

Проверка средней квартиры: `tests/test_studio_apartment_meters.py`, в том числе
исполнение рабочего HTML для дробного U и сравнение потерь/DN без overlays.

```sh
venv/bin/python -m pytest tests/test_studio.py tests/test_water_demand.py \
  tests/test_legacy_sp30_source_parity.py tests/test_wizard.py -q
node scripts/verify_studio_ui.cjs
venv/bin/python -m pytest tests/test_site_shell.py tests/test_deployment_contract.py -q
node scripts/verify_site_shell.cjs
```

Для браузерного теста нужен Playwright и Chrome; при необходимости задать
`PLAYWRIGHT_MODULE` (путь к модулю), `PLAYWRIGHT_CHANNEL`, `STUDIO_URL`.
Он выполняется против отдельного тестового хранилища и создаёт в нём черновики
и PDF-предпросмотр. Не использовать для приёмки на боевом сервере.
Снимки экрана: `output/studio-preview/screenshots/`.
Проверка общей оболочки, возврата к черновику и страниц на 320/768/1440 px:
`output/studio-preview/site/`. `verify_site_shell.cjs` запрещён на внешнем хосте.

Лимиты: 10 PDF, 10 МБ каждый, 100 страниц в файле, 40 МБ на черновик.
Полный multipart-поток ограничен до разбора; неизвестные поля, нечисловые
значения и устаревшие ревизии отклоняются. Пакет с повреждённым PDF не принимается
частично. Дубликаты идентичного файла объединяются по хешу содержимого.
