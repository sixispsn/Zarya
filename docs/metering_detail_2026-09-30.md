## Согласованная топология Г.1 — 14.10.2026

Последующий ответ пользователя: «Повторить и топологию рисунка Г.1».
Нижний рисунок предоставленного ГОСТ (PDF-страница 21) реализован как
`common_topology: gost_g1`: две проходные магистрали, счётчик на общей
перемычке, четыре переключающих затвора, две отдельные обводные ветви
с обратными клапанами, отдельные отсечки входов и выходов. Измерительная
вставка развёрнута на принципиальной схеме: фильтр, счётчик, контрольные
отборы, манометр, отсечки и обратный клапан; третьей обводной внутри неё нет.

`metering_switching.py` задаёт внешние узлы и пути. Их используют СО,
`metering_switching_drawing.py` и проверка обслуживания. Оба выхода ВУ
переданы на лист насосной. При `pre_meter_branch` два независимых отбора В2
остаются до счётчика. Количество: один счётчик; две входные, две выходные,
четыре переключающих, две обводные арматуры; два обратных клапана магистралей
плюс обратный клапан вставки. Опциональные сервисные отсечки учитываются
только при соответствующем выборе.

Два сценария связности проверяют проход от каждого выбранного ввода к обоим
выходам через счётчик при закрытых обводных. Добавленная обходная связь или
разорванная вставка проваливают проверку. Для обслуживания обе наружные сети
и оба выхода здания — потенциальные источники; обратные клапаны не отсечки.
Полное опорожнение и безопасность снятия без профиля/паспортов не подтверждены.

Новые Studio-черновики хранят `common_vu_topology=gost_g1`. Старые без маркера
и YAML без поля сохраняют `merge_before`; явный переход с индивидуального
учёта на общий выбирает новую топологию. Расчётные алгоритмы и подписанный
пример Самары не меняются. Контрольный PDF — отдельная копия этого примера.

DN/длины/электроприводы из примера ГОСТ не копируются. В Самаре DN обводных
не задан, остаётся запросом данных. Потери новой переключающей обвязки не
объявлены включёнными в старый насосный расчёт. Габариты известных изделий
сохранены на размерных листах; полный монтажный габарит не выдумывается.

Проверки: `tests/test_metering_g1_switching.py`, включая вертикальные вставки,
миграцию/round-trip, количественную полноту, связи рисунка, обслуживание,
ПЗ и оба выхода насосной. Повторить: `venv/bin/python scripts/preview_metering_common.py`.
Сборка: 26 страниц с закладками; основной ВУ — первая, насосная — 24-я.
Изменения пока локальные, на сервер не развёрнуты.

Ниже сохранена история предыдущих шагов; ожидание согласования топологии
из следующего раздела закрыто этим явным решением пользователя.

## Что изменено

`app/pz/metering_detail.py` заменяет прежнюю блок-схему техническим чертежом на А3 (420 × 297 мм):

- крупный водомерный узел: запорная арматура, фильтр, счётчик, манометр с отключением, два контрольных шаровых крана с заглушками (п. 12.9 СП 30), обратный клапан;
- обводная только из принятого `MetersSystem.has_bypass`; электропривод обводной — при `need_bypass` именно вводного водомера, а не у любого другого счётчика;
- вводы проходят через условную стену в гильзах, возле них показаны узлы учёта и направления подключения;
- ответвление В2 перед счётчиком рисуется только для явно принятой `pre_meter_branch`. Раздельность систем сама по себе не означает ответвление до учёта;
- при объединённой системе указывается В1+В2; при двух вводах сохраняется существующая модель одинакового узла на каждом вводе, а не копируется общий счётчик из конкретного рисунка ГОСТ;
- таблица: тип, DN, каталожные Qmax/Qmin, отдельный паспортный Qmin, расчётная потеря напора, проверка минимума, АСКУЭ;
- выноски через существующий `LeaderLayoutEngine`, стрелка, горизонтальная полка, текст сверху/снизу, высота 3,5 мм; вспомогательная линия 0,25 мм, основная 0,6 мм;
- встроенный OpenGOST Type B. Текст не растеризуется, лист и УГО векторные.

Расходы, потери, алгоритм подбора и рабочий/архивный legacy не изменены. Используется результат `meters_from_calc`; перед рисованием повторяется существующая проверка Qсред. Неоднозначный, отсутствующий или непригодный по текущему Qсред водомер не рисуется как подтверждённый.

## Входы и сохранение

Необязательная секция YAML проходит `IOS2Request → build_project → Project` без потери данных:

```yaml
metering_detail:
  room_number: '001'
  room_name: Водомерная
  inlet_dn: 50
  bypass_dn: 50
  fire_branch_dn: null
  inlet_elevation_m: -1.50
  meter_model: ''
```

Числа выше — пример заполнения, не значения по умолчанию. Отметка — ось ввода в относительных координатах, а не гарантированный напор и не автоматически отметка насосного коллектора. `inlet_dn` — номинальный DN; внутренний диаметр гидравлического участка не переименовывается в DN. Новых обязательных вопросов в Studio не добавлено; графические сведения можно передать через YAML/модель.

Номер помещения, DN ввода/обводной, модель и паспорт не выдумываются. Недостающие сведения указаны в примечаниях листа и предупреждениях комплекта. Отсутствие данных не выдаётся за нормативное подтверждение. Строка с моделью не заменяет паспортные данные, которые задаются в существующем блоке проверки минимума водомера.

## Интеграция и границы

Экспорт остаётся `generate_metering_scheme_pdf` и `Схема_вводов_и_ВУ.pdf`, поэтому используется существующим комплектом ИОС2 / Studio. На листе до двух вводов; остальные переходят на следующие листы без уменьшения шрифта. SVG-превью возвращает первый лист, PDF — все.

Это принципиальная деталировка стадии П, не монтажный чертёж: не назначены фактические межфланцевые размеры, прямые участки конкретного счётчика, крепления, PN и конструкция герметизации. Нарисованный состав не является новым расчётом потерь и не добавляется автоматически в спецификацию как подтверждённый обмер. Для другого состава узла (параллельные счётчики, разные узлы на разных вводах, общий учёт нескольких вводов) нужно отдельное явное описание топологии; существующая модель этого не выражает.

## Материалы труб внутри одного ВУ

Добавлены независимые `pipe_sections`: `inlet`, `before_meter`, `after_meter`, `outlet`,
`bypass`, `fire_branch`. Они соответствуют маркам У1-У6 на схеме и ведомости труб,
а не системам Т3/Т4 и не позициям арматуры. В одном узле допустимо описывать
разные материалы: сталь, оцинкованную и нержавеющую сталь, медь, ПЭ, PP-R, PE-X,
многослойные и иные трубы. Это поддержка исходных данных, не автоматическое
разрешение применения любого материала в любых условиях.

У каждого участка отдельно сохраняются материал, серия, номинальный DN (если
он известен), наружный диаметр, стенка, способ соединения и источник размеров.
Внутренний диаметр определяется геометрически как Dн-2s, без округления до вывода.
Для полимера размер по наружному диаметру не превращается в DN. Неположительное
сечение, неизвестные поля/материалы и нечисловые размеры отклоняются.

Материал не наследуется из общего текстового поля `cold_mains`: в существующем
общем классификаторе слово «сталь» ведёт к ВГП, что непригодно для произвольной
нержавейки. Этот классификатор и гидравлические алгоритмы не менялись. Данные
ВУ не меняют расчётные расходы, диаметры участков ядра, шероховатость, потери
водомера или насосный подбор. При дальнейшем включении этих труб в гидравлическую
модель понадобится отдельная явная привязка к расчётным участкам.

`support_pipe_section` привязывает хомут к текущим материалу и Dн конкретного
участка. Замена трубы повторно проверяет крепление. Старые ручные сведения
допустимы без привязки; при привязке их противоречие данным участка становится
ошибкой. При удалении привязанной трубы молчаливого возврата к старым размерам
нет. Неподходящий выбранный хомут и труба отсутствующей ветви доходят до
`VU-COMPOSITION`; неизвестные соединители/монтажные размеры не превращены в
новые обязательные поля первичного ввода Studio.

Совпадение DN не подтверждает стык двух систем. Переходные детали, сопряжение
трубы с резьбовой/фланцевой арматурой, уплотнения, монтажные длины, P/T,
температурные перемещения и крепления пока имеют статус требующих проверки.
Из условных длин линий не подсчитывается закупочная спецификация. Модель
по-прежнему описывает однотипный узел на вводах, не разные сборки на каждом вводе.

Пример входа (размер и материал не являются значениями по умолчанию):

```yaml
metering_detail:
  support_pipe_section: inlet
  pipe_sections:
    inlet:
      material: steel
      series: ВГП обыкновенная
      nominal_dn: 50
      outer_diameter_mm: 60
      wall_thickness_mm: 3.5
      joining: threaded
      geometry_source: ГОСТ 3262-75, таблица 1
    outlet:
      material: ppr
      series: VALTEC VTp.700.FB20
      outer_diameter_mm: 63
      wall_thickness_mm: 8.6
      joining: socket_fusion
      geometry_source: ПС 47472, раздел 4; PDF стр. 1
```

В `preview_metering_detail.py --catalogue` показан смешанный пример: ВГП на
вводе/обводе и у счётчика, PP-R на выходе. Стальная геометрия берётся из
существующего явного справочника ВГП, не свободного текстового классификатора.
Геометрия полимера 63×8,6 (dвн=45,8 мм) и метод соединения сверены с
[паспортом производителя VALTEC ПС 47472](https://valtec.ru/document/technical/PPR-FIBER-PN20-0824.pdf),
разделы 4 и 5.2; проверено 30.09.2026, SHA-256 PDF
`89ff9ddbb7d0e5b344ecae3ce03dc04c035b9f43d7d981a1629383a2e31f1e9b`.
Это заданный размер контрольного примера, не новый гидравлический подбор.
Ранее показанный хомут только для нержавейки в этот стальной пример не перенесён.

Дополнительные проверки: `tests/test_metering_pipes.py`. PDF по-прежнему
формируется существующим генератором ИОС2; марки и ведомость присутствуют только
при явном описании труб. Знак диаметра отрисовывается вектором: отсутствующий
глиф OpenGOST не заменяется квадратом в браузере или PDF. Условия сейсмики и
мерзлоты остаются отдельными проверками, выбор материала их не снимает.
