## Комплектность скачивания ZIP — завершена

Ограниченный этап — 100%. Защита ZIP от отсутствующего файла уже существовала
и сохранена. Новый тест подтвердил пробел: пустой документ включался в ZIP
с HTTP 200. Также воспроизведены дубли имён в архиве и ошибка на некорректном
имени в сохранённом списке. Проверки отдельных файлов ранее полагались на
резолвер и отложенное чтение FileResponse; теперь чтение проверяется до ответа.

`app/intake/package_files.py` проверяет простое имя, непустой обычный файл,
читает его и сравнивает размер, inode/device и временные метки до/после
чтения открытого дескриптора. Короткое чтение, изменение метаданных или OSError
дают отказ. Дубли имён, пустой/некорректный список не создают успешный ZIP.
Оба обработчика Studio package используют общий проверенный набор байтов:
отдельный документ возвращается Response, ZIP записывает bytes через writestr,
не перечитывая путь после проверки. При ошибке одного члена собранная в памяти
часть ZIP не отправляется; клиент получает 404 JSON, не частичный архив.

Сохранённый список документов определяет состав этой транспортной проверки;
отсутствие позиции в самом списке не устанавливается заново по нормам.
Авторизация, run_id, версия и stamp проверяются по-прежнему. Резервный путь
`wizard._run_file` к сохранённой копии паспорта сохранён и проверен отдельно.
Физические архивы и черновик не изменяются, документы не пересобираются этим
слоем. Прежнее восстановление run через _get_run не заменялось.

Это не криптографическая аттестация, не проверка структуры PDF и не атомарный
снимок всего файлового дерева в один момент. Уже успешно прочитанные байты
могут быть отправлены, даже если файл позже изменили; повторного чтения нет.
Для ZIP по-прежнему используется память, плюс буфер текущего исходного файла;
одиночный документ теперь также полностью читается до ответа. Автоматическая
перезапись/восстановление архива и новый нормативный допуск не добавлены.

### К1: устаревшие ожидания теста и снимка замечаний

`AGENTS.md`, п. 29, уже запрещает перенос максимумов стояков на горизонтальные
участки. `resolve_k1_main_flows` в `app/pz/wastewater_diagnostics.py` использует
отдельный `pipe_horizontal_flow`; в данном YAML нет достаточных данных для
подтверждения расходов шести горизонтальных участков К1. Результат:
`pending_horizontal_flows` содержит четыре квартирные ветви, К1-М1 и К1-Вып1,
список `hydraulics` пуст. Поэтому рассчитанное h/d К1-М1 и К1-Вып1 больше
не может считаться подтверждённым. K-GOST-08F сообщает о недостающем расчёте.

Старые тесты `test_release_blocker_regression.py` ожидают расчёт по расходам
стояков (в том числе 2,758 л/с) и обращаются к отсутствующей первой строке
гидравлики. Это объясняет AssertionError, IndexError и KeyError данного
прогона. Один тест задаёт только ручной расход без требуемого основания.
Возвращать старый перенос ради зелёного теста запрещено. Следует разделить
неполный неизменённый demo и специально подготовленные синтетические данные
для проверки устаревания гидравлического результата.

### Горячий водомер: воспроизводимый дефект адаптера

В исходном проекте `metering_detail.validate()` возвращает `[]`,
`meter_mounting == "unknown"`, а `meter_orientation(detail, "hot")` возвращает
`"unknown"`. `hot_meter_view` в `app/pz/metering_hot_node.py` создаёт
`meter_orientations={"hot": "unknown"}`. Валидатор `MeteringDetailData` допускает
unknown для общего `meter_mounting`, но не для значений `meter_orientations`.
Производная ветвь поэтому выдаёт ошибку «неизвестный узел/ориентация» и
блокер VU-HOT-COMPOSITION, хотя исходная модель валидна.

Это ошибка согласованности представлений, не новая ошибка legacy-формулы.
Исправление должно сохранить неопределённость положения и отдельную
паспортную проверку; нельзя назначать горизонтальное/вертикальное положение
объекта, считать неизвестную ориентацию подтверждённой или ослаблять проверку
неизвестных строк. До исправления не включать этот дефект в ожидаемые блокеры.
